# Modbus TCP: подключение контроллера по сети

Сервер опрашивает контроллер (например, ОВЕН ПР205) по Ethernet и показывает его значения в клиенте:
температуры, статусы, режимы. Уставки и команды из клиента записываются обратно в контроллер.

```
Контроллер ──Modbus TCP (порт 502)──▶ сервер ──WebSocket──▶ клиент (Vue)
           ◀── запись уставок/команд ──        ◀── команды ──
```

Сервер — **ведущий** (Master/клиент Modbus): сам опрашивает контроллер, контроллер только отвечает.
Что и откуда читать, описывает **карта тегов** `modbusMap.json`.

Без контроллера всё можно проверить на эмуляторе — раздел 6.

---

## 1. Подготовка контроллера и сети

1. Подключите контроллер к той же сети, что и сервер, и задайте ему постоянный IP-адрес
   (в программе-конфигураторе производителя; для ОВЕН — «ОВЕН Логик»).
2. Включите в контроллере **Modbus TCP Slave** (сервер Modbus), порт обычно `502`.
3. Запишите **адрес устройства** (Unit ID, Slave ID) — обычно `1`.
4. Подготовьте таблицу регистров: какие переменные доступны, их адреса, тип данных (int16, float32 …)
   и можно ли в них писать. Её даёт конфигуратор или документация контроллера.
5. Проверьте связь с сервера:
   ```bash
   nc -vz 192.168.10.5 502
   ```
   Ответ `succeeded` / `open` — порт доступен.

## 2. Настройка `conf.env`

```bash
MODBUS_ENABLED=true

MODBUS_DID=igumen          # пользователь (dID), которому показывать значения
MODBUS_DEVICE=pr205        # id устройства по умолчанию для тегов карты
MODBUS_DEVICES='[{
    "id":"pr205",
    "host":"192.168.10.5",
    "port":502,
    "unitId":1
    }]'
```

| Параметр | По умолчанию | Описание |
|---|---|---|
| `MODBUS_ENABLED` | `true` | `false` — Modbus TCP выключен |
| `MODBUS_DID` | — | dID пользователя: значения пишутся в `.configData/<dID>.json` и видны пользователям этого dID. Можно задать и в корне карты (`"dID"`) |
| `MODBUS_DEVICE` | — | `id` устройства из `MODBUS_DEVICES`, к которому относятся теги карты. Можно задать в корне карты (`"deviceId"`) |
| `MODBUS_DEVICES` | — | список контроллеров (JSON): `id` — любое имя, `host`, `port` (502), `unitId` (1). Несколько устройств — несколько объектов в списке |
| `MODBUS_TIMEOUT` | `3000` | сколько ждать ответа, мс |
| `MODBUS_RECONNECT_MIN` / `_MAX` | `1000` / `30000` | пауза перед переподключением после обрыва: от … до мс, удваивается при каждой неудаче |
| `MODBUS_POLL_ERROR_THRESHOLD` | `5` | после стольких ошибок опроса подряд интервал опроса увеличивается… |
| `MODBUS_POLL_BACKOFF_MULTIPLIER` | `2` | …в столько раз… |
| `MODBUS_POLL_MAX_INTERVAL` | `300000` | …но не больше, мс. После первого удачного ответа интервал возвращается к обычному |

`MODBUS_DEVICES` записывается в одинарных кавычках — так JSON читается целиком, даже на нескольких строках.

> Параметр `MODBUS_MAP_FILE` сервер не использует: карта всегда читается из `$DATA_DIR/modbusMap.json`.

## 3. Карта тегов `modbusMap.json`

Карта лежит в папке конфигураций: **`.configData/modbusMap.json`** (`DATA_DIR` в `conf.env`).
Образец — `modbusMap.json` в корне проекта (карта ПР205). Первый раз скопируйте его:

```bash
cp modbusMap.json .configData/modbusMap.json
```

### 3.1. Структура

```json
{
  "pollInterval": 3000,
  "republishMs": 60000,
  "maxGap": 0,
  "tags": [
    {
      "room": "room01", "request": "sensors", "item_name": "dTemp01", "item_type": "num",
      "title": "Гостиная", "group": "Гостиная",
      "table": "holding", "address": 16430, "dataType": "int16", "scale": 0.1,
      "writable": false, "comment": "температура в гостиной"
    },
    {
      "room": "room01", "request": "setpoints", "item_name": "sTemp01", "item_type": "num",
      "table": "holding", "address": 16404, "dataType": "float32", "wordOrder": "LE",
      "decimals": 1, "deadband": 0.05, "writable": true
    }
  ]
}
```

Общие поля карты:

| Поле | По умолчанию | Описание |
|---|---|---|
| `pollInterval` | `1000` | как часто опрашивать контроллер, мс |
| `republishMs` | `60000` | значение без изменений раз в столько мс перезаписывается в файл (клиентам не рассылается) |
| `maxGap` | `0` | сколько «пустых» регистров допускается внутри одного запроса (см. 3.4) |
| `dID`, `deviceId` | из `conf.env` | значения по умолчанию вместо `MODBUS_DID` / `MODBUS_DEVICE` |
| `defaultScale`, `defaultOffset` | `1`, `0` | масштаб и смещение для тегов, где они не заданы |

### 3.2. Поля тега: где показать значение

| Поле | Описание |
|---|---|
| `room` | комната в клиенте: `room01`, `room02`, … (формат `roomNN`) или `common` — вкладка «Общие настройки» |
| `request` | раздел: `sensors` — «Панель управления» (по умолчанию), `system` — «Состояние устройств», `setpoints` — уставки |
| `item_name` | имя параметра; **префикс задаёт подпись в клиенте**, цифры — номер: `dTemp01` — «Температура», `dHum` — «Влажность», `dStatus` — «Статус», `dMode` — «Режим», `aPump` — «Насос», `aRelay` — «Реле», `sTemp` — «Уставка температуры» и т. д. |
| `item_type` | `num` — число, `bool` — да/нет. `dTemp`, `dHum`, `xStatus` сервер сам считает числами, `dBool` — логическим |
| `title`, `group` | заголовок группы (комнаты) в клиенте; берётся у **первого** пришедшего тега комнаты |
| `dID`, `deviceId` | если тег относится к другому пользователю или устройству |
| `comment` | для себя, сервер не читает |

**Уставка рядом с датчиком.** На «Панели управления» уставка показывается в карточке датчика, если:
тег уставки — `request: "setpoints"`, та же `room`, а имя — `s` + тип + тот же номер.
Датчик `dTemp01` ↔ уставка `sTemp01`, датчик `dHum02` ↔ уставка `sHum02`.

### 3.3. Поля тега: где взять значение в контроллере

| Поле | По умолчанию | Описание |
|---|---|---|
| `table` | — | таблица Modbus: `holding` (чтение/запись регистров), `input` (только чтение регистров), `coil` (чтение/запись битов), `discrete` (только чтение битов) |
| `address` | — | адрес **с нуля**, в десятичном виде (см. ниже) |
| `dataType` | `uint16` (регистры), `bool` (биты) | `int16`, `uint16`, `int32`, `uint32`, `float32`; `bool` — только для `coil`/`discrete` |
| `wordOrder` | `BE` | порядок слов 32-битных типов: `BE` — старшее слово первым, `LE` — младшее первым (у ОВЕН float обычно `LE`) |
| `scale`, `offset` | `1`, `0` | значение = сырое × `scale` + `offset` (например, `scale: 0.1`: 215 → 21.5) |
| `decimals` | `3` | знаков после запятой |
| `deadband` | `0` | изменение меньше этого клиентам не рассылается (гасит «дрожание» датчика) |
| `writable` | `false` | `true` — разрешить запись из клиента (только `holding` и `coil`) |
| `interval` | `pollInterval` | свой интервал опроса для тега, мс |

**Адреса.** В карте — адрес протокола, с нуля, в десятичном виде:

| В документации контроллера | В карту |
|---|---|
| `0x4014` (шестнадцатеричный) | `16404` |
| `40001` (нумерация «4xxxx», holding) | `0` |
| `30005` (нумерация «3xxxx», input) | `4` |
| «регистр 1», если нумерация с единицы | `0` |

Логическое значение в регистре (статус 0/1 в `holding`) — `"item_type": "bool"`: клиент получит да/нет,
запись из клиента пишет 1/0.

### 3.4. Как сервер опрашивает

Сервер не опрашивает теги по одному: соседние адреса одной таблицы и одного интервала он собирает в
один запрос (до 100 регистров или 1000 битов). `maxGap` — сколько неиспользуемых регистров можно
захватить между тегами, чтобы объединить их в один запрос. `0` — объединяются только адреса подряд.
Больше запросов — больше нагрузка на сеть, но некоторые контроллеры отвечают ошибкой на чтение
«дыр» в карте регистров — тогда оставьте `0`.

После правки карты **перезапустите сервер** — карта читается при старте.

## 4. Запуск и проверка

1. Запустите сервер: `npm start`.
2. В логе:
   ```
   [ModbusManager] - ➕ Добавляем устройство pr205 (192.168.10.5:502, unitId=1)
   [modbusBridge] - читаем карту тегов: /…/.configData/modbusMap.json
   [modbusBridge] - собрано блоков опроса: 5 (maxGap=0)
   [modbusBridge] - pr205/blk_holding_16404: holding 16404..16405 каждые 3000 мс, тегов: 1
   [modbusBridge] - ✅ инициализация завершена: тегов 27, блоков опроса 5, deviceId=pr205, dID=igumen
   ```
3. Откройте клиент пользователем с dID из `MODBUS_DID`. Значения появятся на вкладках
   «Панель управления» (`sensors`), «Состояние устройств» (`system`), «Общие настройки» (`room: "common"`).
4. Измените уставку в клиенте — в логе `📥 команда от VUE … ✅ записано pr205/sTemp01 = 22`.

Значения также сохраняются в `.configData/<dID>.json` — после перезапуска клиент сразу видит последние.

---

## 5. Запись из клиента

Клиент пишет в контроллер только теги с `"writable": true` в таблицах `holding` или `coil`.

| Ситуация | Что видит пользователь |
|---|---|
| запись прошла | новое значение у всех клиентов этого dID |
| тег без `writable` | ошибка «Тег … доступен только для чтения» (`READ_ONLY`) |
| контроллер не ответил / ошибка | ошибка записи (`MODBUS_ERROR`), значение не меняется |
| значение вне диапазона типа (например, 70000 в `int16`) | ошибка «Значение … вне диапазона типа» |

## 6. Проверка без контроллера: эмулятор

Эмулятор отвечает по той же карте, что и сервер.

1. В отдельном терминале запустите эмулятор:
   ```bash
   node tools/modbusSlaveEmulator.js --map .configData/modbusMap.json --port 5020 --jitter
   ```
   `--jitter` — значения датчиков будут понемногу меняться.
2. В `conf.env` временно направьте сервер на эмулятор:
   ```bash
   MODBUS_DEVICES='[{"id":"pr205","host":"127.0.0.1","port":5020,"unitId":1}]'
   ```
3. Запустите сервер (`npm start`) и откройте клиент.
4. В терминале эмулятора доступны команды:

   | Команда | Действие |
   |---|---|
   | `list` | все теги и текущие значения |
   | `get dTemp01` | значение тега |
   | `set dTemp01 25.5` | изменить значение — клиент покажет его через `pollInterval` |
   | `jitter on` / `jitter off` | дрожание значений |
   | `quit` | выход |

5. Измените уставку в клиенте и проверьте её в эмуляторе: `get sTemp01`.

Не забудьте вернуть настоящий адрес в `MODBUS_DEVICES`.

---

## 7. Диагностика: прочитать все теги

Читает каждый тег карты прямо из контроллера (или эмулятора) и печатает сырые регистры и итоговое
значение — так проще всего найти ошибку адреса, типа или порядка слов:

```bash
node tools/modbusDiag.js --host 192.168.10.5 --port 502 --unit 1 --map .configData/modbusMap.json
```

Сервер при этом можно не останавливать. Код выхода: `0` — всё прочитано, `1` — были ошибки.

## 8. Если что-то не работает

| Признак | Причина и решение |
|---|---|
| В логе `Modbus отключён (MODBUS_ENABLED=false)` | включите `MODBUS_ENABLED=true` |
| `не удалось прочитать карту тегов …/modbusMap.json` | нет файла в `.configData` или ошибка JSON — скопируйте образец (раздел 3) и проверьте запятые/скобки |
| `dID не задан` / `deviceId не задан` | задайте `MODBUS_DID` / `MODBUS_DEVICE` в `conf.env` или `"dID"` / `"deviceId"` в корне карты |
| `deviceId "pr205" отсутствует в MODBUS_DEVICES` | `MODBUS_DEVICE` не совпадает с `id` в `MODBUS_DEVICES` или там ошибка JSON (`MODBUS_DEVICES: невалидный JSON`) |
| `тег #N (…): не задано поле …`, `некорректный address`, `bool допустим только для coil/discrete` | ошибка в описании тега — тег пропущен, остальные работают |
| `❌ ошибка опроса pr205:blk_…: Timed out` / `ECONNREFUSED` | контроллер недоступен: IP, порт, кабель, включён ли Modbus TCP в контроллере (раздел 1, `nc -vz`) |
| `Illegal data address` (код 2) | такого адреса нет в контроллере: проверьте `address` и таблицу; при `maxGap` > 0 уменьшите до `0` |
| Значение странное (огромное, отрицательное, 0) | неверный `dataType` или `wordOrder` для 32-битных; сравните с `tools/modbusDiag.js` |
| Значение в 10 раз больше/меньше | нужен `scale: 0.1` (или `10`) |
| Значения есть в логе, но не в клиенте | пользователь вошёл с другим dID, чем `MODBUS_DID`; `room` не в формате `roomNN`/`common` |
| Уставка не показывается в карточке датчика | имя уставки не `s` + тип + номер датчика или другая `room` (раздел 3.2) |
| Интервал опроса растёт в логе (`интервал опроса увеличен`) | серия ошибок связи; после восстановления связи вернётся сам |
