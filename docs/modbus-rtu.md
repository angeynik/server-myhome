# Modbus RTU: устройства на шине RS-485

Сервер работает с устройствами Modbus RTU по последовательной шине RS-485 (два провода A и B).
Бывает в двух ролях — их можно включать по отдельности или вместе:

| Роль | Кто кого опрашивает | Зачем |
|---|---|---|
| **Master** (ведущий) | сервер опрашивает устройства | котёл, счётчик, датчики, реле: значения — в клиент, уставки и команды из клиента — в устройство |
| **Slave** (ведомый) | внешний контроллер (ПЛК, SCADA) опрашивает сервер | сервер отдаёт внешнему контроллеру свои значения и принимает от него записи |

```
           RS-485 (шина 1)                          RS-485 (шина 2)
устройства ◀──── Master ──── сервер ──── Slave ────▶ внешний контроллер
                               │
                            клиент (Vue)
```

Без железа всё проверяется на виртуальных портах — раздел 8.

## 1. Оборудование

### 1.1. Адаптер RS-485

- **USB-RS485 переходник** — самый простой вариант для любого компьютера (Linux, macOS, Raspberry Pi,
  Orange Pi). Выбирайте с автоматическим переключением направления передачи (большинство готовых
  USB-адаптеров такие).
- **Встроенный UART одноплатника + модуль RS-485** — возможен, но модуль должен сам переключать
  приём/передачу (auto-direction, например на MAX13487E). Модули на MAX485 с ручным выводом DE/RE
  из Node.js работают ненадёжно: обрезаются первый/последний байты кадра.

Для одновременной работы **Master и Slave нужны два разных адаптера** (две шины): Modbus RTU —
шина с одним ведущим, один порт на обе роли не поделить (раздел 4.3).

### 1.2. Подключение проводов

- `A` (иногда `D+`, `Data+`) — ко всем `A`, `B` (`D-`, `Data-`) — ко всем `B`. Шина — одна линия
  «цепочкой» от устройства к устройству, без звёзд и длинных отводов.
- На **двух концах** линии — терминаторы 120 Ом между A и B (часто включаются перемычкой на устройстве
  или адаптере). На коротких линиях (несколько метров) обычно работает и без них.
- Желательно соединить `GND` адаптера и устройств (третий провод), особенно при разном питании.
- Если связи нет совсем — первым делом поменяйте местами A и B: производители обозначают их по-разному.

### 1.3. Имя порта

| Система | Как найти | Пример |
|---|---|---|
| Linux, Raspberry Pi, Orange Pi | `ls /dev/ttyUSB* /dev/ttyACM*` (USB), `ls /dev/ttyS*` (UART) | `/dev/ttyUSB0`, `/dev/ttyS3` |
| macOS | `ls /dev/cu.*` | `/dev/cu.usbserial-1420` |

Удобный способ: выполните команду до и после подключения адаптера — появившийся порт и есть нужный.
На macOS используйте `/dev/cu.*`, не `/dev/tty.*`. Адаптерам на CH340 может понадобиться драйвер.

**Linux — права на порт.** Пользователь, от которого запускается сервер, должен быть в группе `dialout`:

```bash
sudo usermod -aG dialout $USER     # затем выйдите из системы и войдите снова
```

**Orange Pi / Raspberry Pi — встроенный UART** нужно включить: `armbian-config` → System → Hardware →
нужный `uartX` (или `overlays=uart3` в `/boot/orangepiEnv.txt`) и перезагрузиться.

## 2. Параметры шины

У всех устройств на одной шине и у сервера должны совпадать:

| Параметр | Типичное значение | Где посмотреть |
|---|---|---|
| скорость (`baudRate`) | 9600 или 19200 | меню/документация устройства |
| чётность (`parity`) | `none`, `even` или `odd` | там же; «8N1» = 8 бит, без чётности, 1 стоп-бит, «8E1» = чётность even |
| биты данных (`dataBits`) | 8 | |
| стоп-биты (`stopBits`) | 1 (2 — при `none` в строгих устройствах) | |

У каждого устройства — свой **адрес** (Slave ID, 1…247), на шине адреса не должны повторяться.

---

## 3. Включение в `conf.env`

```bash
MODBUS_RTU_ENABLED=true
MODBUS_RTU_CONF=./modBus/modbusConf.json
#MODBUS_ROLE=master          # необязательно: master | slave | both — важнее "role" из файла
```

Конфигурация шины и устройств — в `modBus/modbusConf.json`. Образец со всеми полями —
`modBus/modbusConf.example.json`:

```bash
cp modBus/modbusConf.example.json modBus/modbusConf.json
```

Ошибка RTU (нет порта, неверный файл) пишется в лог и **не мешает** работе остального сервера.

## 4. Файл `modbusConf.json`

### 4.1. Роль

```json
{ "role": "master", "master": { … }, "slave": { … } }
```

| `role` | Что запускается |
|---|---|
| `master` | только секция `master` |
| `slave` (по умолчанию) | только секция `slave` |
| `both` | обе — на **разных** портах |

### 4.2. Master: сервер опрашивает устройства

```json
"master": {
  "port": "/dev/ttyUSB0",
  "baudRate": 9600, "dataBits": 8, "stopBits": 1, "parity": "none",
  "pollIntervalMs": 2000,
  "requestTimeoutMs": 300,
  "interRequestDelayMs": 20,
  "devices": [
    {
      "id": "boiler", "dID": "igumen", "room": "room02", "slaveId": 1,
      "registers": [
        { "name": "dTemp01", "type": "holding", "address": 0, "dataType": "int16", "scale": 0.1, "deadband": 0.1, "title": "Котёл", "group": "Котельная" },
        { "name": "sTemp01", "type": "holding", "address": 1, "dataType": "int16", "scale": 0.1, "request": "setpoints", "writable": true },
        { "name": "aPump01", "type": "coil", "address": 0, "dataType": "bool", "request": "system", "writable": true },
        { "name": "dPress01", "type": "input", "address": 2, "dataType": "float32", "swapWords": true }
      ]
    },
    {
      "id": "meter", "dID": "igumen", "room": "room03", "slaveId": 2,
      "registers": [
        { "name": "dVoltage01", "type": "holding", "address": 0, "dataType": "uint16", "scale": 0.1 }
      ]
    }
  ]
}
```

**Шина:**

| Поле | По умолчанию | Описание |
|---|---|---|
| `port` | — | порт адаптера (раздел 1.3) |
| `baudRate`, `dataBits`, `stopBits`, `parity` | 9600, 8, 1, `none` | параметры шины (раздел 2) |
| `pollIntervalMs` | 2000 | пауза между полными циклами опроса всех устройств, мс |
| `requestTimeoutMs` | 300 | сколько ждать ответа устройства, мс |
| `interRequestDelayMs` | 20 | пауза между запросами на шине (медленным устройствам — 50–100) |

**Устройство** (`devices[]`):

| Поле | Описание |
|---|---|
| `id` | уникальное имя устройства на шине (по умолчанию = `dID`). **Обязательно**, если у нескольких устройств один `dID` |
| `dID` | пользователь, которому показывать значения: они пишутся в `.configData/<dID>.json` |
| `slaveId` | адрес устройства на шине (1…247) |
| `room` | комната в клиенте для регистров устройства: `room01`, `room02`, … или `common` |
| `registers` | регистры (ниже) |

**Регистр** (`registers[]`):

| Поле | По умолчанию | Описание |
|---|---|---|
| `name` | — | имя параметра; **префикс задаёт подпись в клиенте**: `dTemp` — «Температура», `dHum` — «Влажность», `dPress` — «Давление», `dVoltage` — «Напряжение», `dPower` — «Потребление», `aPump` — «Насос», `aRelay` — «Реле», `dStatus` — «Статус», `sTemp` — «Уставка температуры» и т. д.; цифры в конце — номер |
| `type` | — | `holding`, `input`, `coil`, `discrete` |
| `address` | — | адрес с нуля, десятичный (как в [Modbus TCP, раздел 3.3](modbus-tcp.md#33-поля-тега-где-взять-значение-в-контроллере)) |
| `dataType` | — | `int16`, `uint16`, `int32`, `uint32`, `float32`, `bool` |
| `scale` | 1 | значение = сырое × `scale` (например, `0.1`: 215 → 21.5) |
| `swapWords` | `false` | 32-битные типы: младшее слово первым (если значение «нелепое» — попробуйте `true`) |
| `request` | `sensors` | `sensors` — «Панель управления», `system` — «Состояние устройств», `setpoints` — уставки |
| `room` | `room` устройства | своя комната для регистра |
| `item_type` | по значению | `num` или `bool` |
| `writable` | `false` | `true` — разрешить запись из клиента (только `holding` и `coil`) |
| `deadband` | 0 | изменение меньше этого клиентам не рассылается |
| `title`, `group` | — | заголовок комнаты в клиенте (берётся у первого пришедшего значения комнаты) |

**Уставка рядом с датчиком:** регистр уставки с `"request": "setpoints"`, той же `room` и именем
`s` + тип + номер датчика: `dTemp01` ↔ `sTemp01`.

Каждый регистр читается отдельным запросом, устройства — по очереди. Время цикла ≈
число регистров × (время ответа + `interRequestDelayMs`) + `pollIntervalMs`. На 9600 бод ответ на
чтение одного регистра — около 10–20 мс.

### 4.3. Slave: внешний контроллер опрашивает сервер

```json
"slave": {
  "port": "/dev/ttyUSB1",
  "baudRate": 9600, "dataBits": 8, "stopBits": 1, "parity": "none",
  "unitId": 10,
  "dID": "igumen",
  "room": "common",
  "registerMap": [
    { "name": "dMove01", "type": "discrete", "address": 0, "dataType": "bool", "initial": false },
    { "name": "sTemp01", "type": "holding", "address": 0, "dataType": "int16", "scale": 0.1, "initial": 22 },
    { "name": "aRelay01", "type": "coil", "address": 0, "dataType": "bool", "initial": false }
  ]
}
```

| Поле | По умолчанию | Описание |
|---|---|---|
| `port`, `baudRate`, `dataBits`, `stopBits`, `parity` | —, 9600, 8, 1, `none` | порт и параметры шины внешнего контроллера |
| `unitId` | 21 | адрес сервера на этой шине — его указывают во внешнем контроллере |
| `dID`, `room` | — | кому и в какую комнату показывать записи внешнего контроллера |
| `holdingRegistersSize` … `discreteInputsSize` | 100 | размер каждой таблицы (адреса 0…N−1) |
| `crcCheck` | `true` | отбрасывать кадры с неверной контрольной суммой (помехи) |
| `registerMap[]` | — | регистры: поля как у Master + `initial` — значение при старте **в итоговых единицах** (с `scale: 0.1` значение `22` хранится как 220) |

- Внешний контроллер **читает** любые таблицы, **пишет** — в `holding` и `coil`.
- Запись внешнего контроллера в регистр из `registerMap` сразу показывается в клиенте
  (раздел `system` комнаты `room`, если у регистра не задан свой `request`).
- Значения, которые сервер отдаёт внешнему контроллеру, обновляет код сервера:
  `modbusRtuBridge.setSlaveValue('dMove01', true)` (например, из обработчика датчика GPIO).

**Один порт на обе роли нельзя.** При `"role": "both"` и одинаковых `master.port` и `slave.port`
сервер не запустит RTU и напишет об этом в лог. Флаг `"allowSharedPort": true` снимает проверку,
но работать такая схема не будет — нужен второй адаптер.

## 5. Запуск и проверка

1. Запустите сервер: `npm start`.
2. В логе:
   ```
   [ModbusManager] - Запуск в роли: master
   [ModbusMaster] - Порт /dev/ttyUSB0 открыт (baudRate=9600)
   [Serverapp] - Modbus RTU запущен: тегов Master 5, Slave 0
   ```
3. Откройте клиент пользователем с dID устройства: значения — на вкладках «Панель управления»
   (`sensors`), «Состояние устройств» (`system`), «Общие настройки» (`room: "common"`).
4. Измените уставку (`sTemp01`) — в логе `записано igumen/sTemp01 = 22`.

После правки `modbusConf.json` **перезапустите сервер**.

---

## 6. Запись из клиента

| Ситуация | Что видит пользователь |
|---|---|
| запись прошла | новое значение у всех клиентов этого dID |
| регистр без `"writable": true` или `input`/`discrete` | «Тег … доступен только для чтения» (`READ_ONLY`) |
| нечисловое значение | «Некорректное значение» (`BAD_VALUE`) |
| устройство не ответило | «Не удалось записать значение в устройство» (`MODBUS_ERROR`) |

## 7. Проверка связи до настройки сервера

Удобно убедиться, что устройство отвечает, отдельной программой — до правки `modbusConf.json`:

- **Windows:** Modbus Poll, QModMaster;
- **Linux/macOS:** `mbpoll` (`sudo apt install mbpoll` / `brew install mbpoll`):
  ```bash
  # 2 holding-регистра с адреса 0, устройство 1, 9600 8N1
  mbpoll -m rtu -a 1 -b 9600 -P none -t 4 -r 1 -c 2 /dev/ttyUSB0
  ```
  В `mbpoll` нумерация регистров **с единицы** (`-r 1` — это `address: 0` в конфиге).

Пока сервер запущен, порт занят им — остановите сервер на время проверки.

## 8. Проверка без железа

```bash
node tools/modbusRtuCheck.js            # все сценарии
node tools/modbusRtuCheck.js master     # Master опрашивает Slave
node tools/modbusRtuCheck.js crc        # отбрасывание кадров с неверным CRC
node tools/modbusRtuCheck.js manager    # роль both: свой Master и свой Slave на двух шинах
```

Инструмент сам создаёт пары виртуальных портов (нужен `python3`, Linux или macOS) и печатает
результат каждой проверки; в конце — `ИТОГ: все проверки прошли`.

## 9. Если что-то не работает

| Признак | Причина и решение |
|---|---|
| В логе `Modbus RTU отключён` | `MODBUS_RTU_ENABLED=true` в `conf.env` |
| `Modbus RTU не запущен: ENOENT … modbusConf.json` | нет файла — скопируйте образец (раздел 3) |
| `Ошибка открытия порта …: No such file or directory` | неверное имя порта или адаптер не подключён (раздел 1.3) |
| `… Permission denied` | Linux: пользователь не в группе `dialout` (раздел 1.3) |
| `… Resource busy` / `Cannot lock port` | порт занят другой программой (Modbus Poll, mbpoll, второй экземпляр сервера) |
| `Master и Slave настроены на один и тот же порт` | роль `both` требует два адаптера (раздел 4.3) |
| `Роль "slave" требует секцию config.slave` | нет секции для выбранной роли; проверьте `role` и `MODBUS_ROLE` |
| `Ошибка чтения boiler.dTemp01 (slaveId=1): Timed out` | устройство не отвечает: адрес `slaveId`, скорость, чётность, перепутаны A/B, нет питания |
| `… Illegal data address` | нет такого регистра: проверьте `address` (с нуля!) и `type` |
| `CRC error` или ответы через раз | помехи: терминаторы, общий GND, экранированная витая пара, ниже скорость; увеличьте `requestTimeoutMs` |
| Значение «нелепое» (огромное, отрицательное) | неверный `dataType`; для 32-битных — `swapWords` |
| Значение в 10 раз больше/меньше | `scale: 0.1` (или `10`) |
| `устройство "…" повторяется — задайте каждому устройству уникальный "id"` | у двух устройств одинаковый `id` (или оба без `id` с одним `dID`) |
| `устройство с недопустимым dID` | `dID` — только латиница, цифры, `_` и `-` |
| Значения в логе есть, в клиенте нет | вход под другим dID; `room` не в формате `roomNN`/`common` |
| Внешний контроллер не получает ответа от сервера (Slave) | `unitId` сервера не совпадает с адресом в контроллере; параметры шины; включена ли роль `slave`/`both` |
