# Камеры видеонаблюдения: муляжи и реальные камеры

Сервер показывает в клиенте (вкладка **«Видеонаблюдение»**) до 16 камер. Каждая камера — это
либо **муляж** (ffmpeg рисует тестовую картинку, устройство не нужно), либо **реальная камера**
по RTSP. Муляжи и реальные камеры можно смешивать: подключили камеру — заменили один муляж,
остальные продолжают работать.

Все камеры описаны в одном файле `cameras.json`. Сервер следит за ним: после сохранения изменения
применяются через 2–3 секунды **без перезапуска сервера**, клиент сам получает новый список.

---

## 1. Подготовка (один раз)

### 1.1. Установите ffmpeg

И муляжи, и реальные камеры работают через ffmpeg.

| Система | Команда |
|---|---|
| macOS | `brew install ffmpeg` |
| Debian / Ubuntu / Raspberry Pi OS | `sudo apt install ffmpeg` |

Проверка — команда должна вывести версию:

```bash
ffmpeg -version
```

Если ffmpeg установлен не в стандартное место, укажите полный путь в `conf.env`:
`FFMPEG_PATH=/opt/homebrew/bin/ffmpeg`.

### 1.2. Проверьте `conf.env`

| Параметр | Значение | Зачем |
|---|---|---|
| `VIDEO_ENABLED` | `true` (или не задан) | видео включено |
| `DATA_DIR` | например `./.configData` | папка со всеми конфигурациями — в ней сервер создаст `cameras.json` |
| `VIDEO_DID` | см. 1.3 | кто видит камеры, у которых в `cameras.json` нет своего `dID` (и муляжи) |
| `VIDEO_MOCK_CAMERAS` | `4` (по умолчанию) | сколько муляжей создать при первом запуске (0–16) |
| `VIDEO_RTSP_URL` | пусто | устаревший параметр одной камеры: если задан, при создании `cameras.json` адрес попадёт в файл первой камерой `cam01`; после этого параметр не используется |

Все камеры после первого запуска — только в `cameras.json`. Параметры `conf.env` из этого раздела
влияют лишь на то, каким файл **создаётся**.

#### Если сервер пишет «переменные окружения терминала перекрывают conf.env»

Кроме `conf.env`, параметры может задавать сам терминал: когда-то в его файл настроек (на macOS — `~/.zshrc`)
могли вписать строку вида `export VIDEO_RTSP_URL=…`. Такое значение главнее `conf.env`, и правка `conf.env`
на него не действует. Сервер при старте называет такие параметры (только имена, без значений):

```
[ERROR] [Serverapp] - переменные окружения терминала перекрывают conf.env …: VIDEO_RTSP_URL
```

Как найти и убрать (macOS):

1. Проверьте, задано ли значение. Пустой вывод — всё в порядке:
   ```bash
   echo $VIDEO_RTSP_URL
   ```
2. Найдите, в каком файле оно записано:
   ```bash
   grep -n VIDEO ~/.zshrc ~/.zprofile ~/.bash_profile ~/.profile 2>/dev/null
   ```
   Ответ вида `/Users/<вы>/.zshrc:12:export VIDEO_RTSP_URL=rtsp://…` — файл `~/.zshrc`, строка 12.
3. Откройте этот файл, удалите строку и сохраните:
   ```bash
   open -e ~/.zshrc
   ```
4. Закройте терминал полностью и откройте новый (в VS Code — удалите вкладку терминала значком корзины
   и создайте новую). Повторите шаг 1 — вывод должен быть пустым.

Если `grep` ничего не нашёл, а `echo` выводит адрес — `export` был набран вручную в этом окне
терминала: просто откройте новый терминал. В VS Code проверьте ещё настройку
`terminal.integrated.env.osx` (Settings → поиск `terminal env`).

Для камер это уже не критично: если адрес из терминала попал в `cameras.json` камерой `cam01`,
просто исправьте или удалите эту камеру в файле.

### 1.3. Кто видит камеры: `VIDEO_DID`

Каждый пользователь сервера привязан к источнику данных — dID (например `igumen`, `poddy_base`).
Камеру видят только пользователи, чей dID указан у камеры. `VIDEO_DID` задаёт значение по умолчанию
для всех камер; у отдельной камеры его можно переопределить полем `dID` в `cameras.json` (раздел 6).

| Запись в `conf.env` | Кто видит камеры |
|---|---|
| `VIDEO_DID=igumen` | только пользователи dID `igumen` |
| `VIDEO_DID='["igumen", "poddy_base"]'` | пользователи `igumen` и `poddy_base` |
| `VIDEO_DID=igumen,poddy_base` | то же самое, короткая запись |
| `VIDEO_DID=*` | все пользователи сервера |
| не задан | реальные камеры — `DEFAULT_USER_DID`, муляжи — все пользователи |

Список берите в одинарные кавычки — так он гарантированно прочитается целиком. Список dID на сервере
виден в логе при старте: `userStore: users=[…], datasources=[poddy_base, igumen]`.

`VIDEO_DID` применяется к муляжам при **создании** `cameras.json` — значение записывается в
`defaults.dID`. Если файл уже создан, поменяйте `"dID"` в его блоке `defaults` (или удалите файл,
и сервер создаст его заново).

Значение без кавычек или с ошибкой (например, незакрытая скобка) — камеры не запустятся, в логе будет
`недопустимый dID …`.

## 2. Первый запуск — муляжи

1. Запустите сервер:
   ```bash
   npm start
   ```
2. В логе сервера должны появиться строки с **полным путём** к файлу:
   ```
   [videoHub] - создан /Users/<вы>/…/serverApp/.configData/cameras.json: 4 муляжей (source "test"), видны всем пользователям (dID "*"); …
   [videoHub] - init: камер 4 из /Users/<вы>/…/serverApp/.configData/cameras.json: cam01 (муляж), cam02 (муляж), cam03 (муляж), cam04 (муляж)
   ```
   Строка `создан …` бывает только при первом запуске; при следующих — только `init: камер N из <путь>`.
   Если был задан `VIDEO_RTSP_URL`, в строке будет `камера из VIDEO_RTSP_URL (cam01) и 4 муляжей`.

   Папка `.configData` начинается с точки, поэтому Finder её не показывает: нажмите `Cmd + Shift + .`
   или откройте файл из терминала — `open -e .configData/cameras.json`. В VS Code она видна в дереве файлов.
3. Откройте клиент и перейдите на вкладку **«Видеонаблюдение»**. Через 1–5 секунд на карточках
   появятся цветные тестовые картинки с бегущим таймером (у каждой камеры свой оттенок).
4. Нажмите на карточку — камера откроется на весь экран, кадр обновляется раз в секунду.

Созданный файл выглядит так:

```json
{
  "defaults": {
    "dID": "*",
    "minLevel": 1,
    "previewIntervalMs": 5000,
    "fullIntervalMs": 1000,
    "maxWidth": 640,
    "quality": 5,
    "archive": false
  },
  "cameras": [
    { "id": "cam01", "title": "Камера 1 (муляж)", "source": "test", "test": { "size": "1280x720", "rate": 10, "noise": 20 } },
    { "id": "cam02", "title": "Камера 2 (муляж)", "source": "test", "test": { "size": "1280x720", "rate": 10, "noise": 20 } },
    { "id": "cam03", "title": "Камера 3 (муляж)", "source": "test", "test": { "size": "1280x720", "rate": 10, "noise": 20 } },
    { "id": "cam04", "title": "Камера 4 (муляж)", "source": "test", "test": { "size": "1280x720", "rate": 10, "noise": 20 } }
  ]
}
```

Файл создаётся только если его нет. Дальше сервер его не перезаписывает — правьте смело.

## 3. Настройка муляжей

Всё делается правкой `cameras.json` и сохранением файла.

- **Больше муляжей** (до 16) — скопируйте строку камеры и поменяйте `id` (`cam05`, `cam06`, …) и `title`.
- **Убрать камеру** — удалите строку или поставьте `"enabled": false`.
- **Приблизить муляж к реальной камере** — блок `test`:
  - `size` — разрешение источника (`"1920x1080"` — как у Full HD камеры);
  - `rate` — кадров в секунду источника (`25` — как у камеры);
  - `noise` — шум 0–100: чем больше, тем крупнее JPEG (реальная картинка обычно ближе к 20–40).

  Чем больше `size` и `rate`, тем больше нагрузка на процессор — так можно заранее проверить,
  потянет ли сервер нужное число реальных камер (см. раздел 7).

После сохранения в логе появится:

```
[videoHub] - reload: добавлены [cam05], изменены [], удалены []; камер 5: …
```

## 4. Подключение реальной камеры (замена муляжа)

### Шаг 1. Узнайте IP-адрес камеры

В приложении камеры, в списке клиентов роутера или программой производителя (SADP у Hikvision,
ConfigTool у Dahua). Лучше закрепить за камерой постоянный IP в настройках роутера.

### Шаг 2. Включите RTSP и создайте пользователя

В веб-интерфейсе камеры (обычно `http://<IP-камеры>`):
- включите RTSP (порт по умолчанию 554);
- заведите отдельного пользователя только для просмотра — его логин и пароль пойдут в адрес.

### Шаг 3. Соберите RTSP-адрес

Формат: `rtsp://логин:пароль@IP:554/путь`. Путь зависит от производителя:

| Производитель | Основной поток | Дополнительный (лёгкий) поток |
|---|---|---|
| Hikvision, HiWatch | `/Streaming/Channels/101` | `/Streaming/Channels/102` |
| Dahua, IMOU | `/cam/realmonitor?channel=1&subtype=0` | `/cam/realmonitor?channel=1&subtype=1` |
| Reolink | `/h264Preview_01_main` | `/h264Preview_01_sub` |
| TP-Link Tapo / VIGI | `/stream1` | `/stream2` |
| Другие | см. инструкцию камеры или ONVIF Device Manager | |

**Рекомендация:** используйте **дополнительный поток**. Для миниатюр и полного экрана в браузере его
разрешения хватает, а нагрузка на сервер в разы меньше. Основной поток нужен только для архива (раздел 6).

**Спецсимволы в пароле** нужно закодировать, иначе адрес разберётся неправильно:

| Символ | Замена |
|---|---|
| `@` | `%40` |
| `:` | `%3A` |
| `/` | `%2F` |
| `#` | `%23` |
| `?` | `%3F` |
| `%` | `%25` |

Пример: пароль `Pa@ss:1` → `Pa%40ss%3A1`.

### Шаг 4. Проверьте адрес на машине сервера

```bash
ffmpeg -rtsp_transport tcp -i "rtsp://viewer:Pa%40ss%3A1@192.168.1.100:554/Streaming/Channels/102" -frames:v 1 -y test.jpg
```

Должен появиться файл `test.jpg` с кадром камеры. Кавычки обязательны (в адресах Dahua есть `&` и `?`).
Если команда не сработала — исправляйте адрес здесь, до правки `cameras.json` (раздел 8).

### Шаг 5. Замените муляж в `cameras.json`

Было:

```json
{ "id": "cam01", "title": "Камера 1 (муляж)", "source": "test", "test": { "size": "1280x720", "rate": 10, "noise": 20 } },
```

Стало:

```json
{ "id": "cam01", "title": "Ворота", "dID": "igumen", "source": "rtsp://viewer:Pa%40ss%3A1@192.168.1.100:554/Streaming/Channels/102" },
```

**Укажите `dID`** — кому показывать камеру: `"igumen"`, или несколько: `["igumen", "poddy_base"]`.
Без него реальная камера унаследует `"*"` из `defaults` и будет видна всем пользователям сервера —
сервер предупредит об этом в логе (`видна всем пользователям — укажите dID`).

Блок `test` можно удалить — для реальной камеры он не используется. `id` лучше оставить прежним:
камера останется на своём месте в сетке.

### Шаг 6. Сохраните файл и проверьте

Через 2–3 секунды в логе:

```
[videoHub] - reload: добавлены [], изменены [cam01], удалены []; камер 4: cam01, cam02 (муляж), cam03 (муляж), cam04 (муляж)
```

В клиенте карточка переименуется в «Ворота», через несколько секунд появится изображение с камеры.
Пароль в логах сервера скрывается.

Повторяйте шаги 1–6 для каждой камеры, пока муляжей не останется.

## 5. Пример: смешанный режим

Две реальные камеры, один муляж и одна выключенная:

```json
{
  "defaults": {
    "dID": "igumen",
    "minLevel": 1,
    "previewIntervalMs": 5000,
    "fullIntervalMs": 1000,
    "maxWidth": 640,
    "quality": 5,
    "archive": false
  },
  "cameras": [
    { "id": "cam01", "title": "Ворота", "source": "rtsp://viewer:pass@192.168.1.100:554/Streaming/Channels/102" },
    { "id": "cam02", "title": "Двор",   "dID": ["igumen", "poddy_base"], "source": "rtsp://viewer:pass@192.168.1.101:554/cam/realmonitor?channel=1&subtype=1" },
    { "id": "cam03", "title": "Гараж (муляж)", "source": "test", "test": { "size": "1280x720", "rate": 10, "noise": 20 } },
    { "id": "cam04", "title": "Склад", "source": "test", "enabled": false }
  ]
}
```

Здесь `dID` в `defaults` — `"igumen"`: все камеры видны этому dID, «Двор» — ещё и `poddy_base`.
Значения из `defaults` действуют на все камеры; любое из них можно переопределить в строке камеры
(например, `"minLevel": 3` — камеру видит только администратор).

## 6. Справочник полей

| Поле | По умолчанию | Описание |
|---|---|---|
| `id` | — (обязательно) | латиница, цифры, `_` и `-`, до 32 символов, уникальный |
| `title` | = `id` | подпись в интерфейсе, до 64 символов |
| `source` | — (обязательно) | `rtsp://…`, `rtsps://…` или `test` (муляж) |
| `dID` | `VIDEO_DID` или `DEFAULT_USER_DID` (у муляжей без `VIDEO_DID` — `"*"`) | кто видит камеру: `"igumen"`, список `["igumen", "poddy_base"]` или `"*"` — все пользователи (раздел 1.3) |
| `minLevel` | `VIDEO_MIN_LEVEL` (1) | минимальный уровень пользователя: 1, 2 или 3 |
| `enabled` | `true` | `false` — камера не запускается |
| `previewIntervalMs` | `VIDEO_SNAPSHOT_INTERVAL_MS` (5000) | как часто обновляется миниатюра, мс (не меньше 500) |
| `fullIntervalMs` | 1000 | как часто обновляется полный экран, мс (не меньше 200) |
| `maxWidth` | 640 | ширина кадра, пикселей; 0 — без уменьшения |
| `quality` | `VIDEO_SNAPSHOT_QUALITY` | качество JPEG: 2 — лучшее … 31 — худшее |
| `archive` | `false` | `true` — запись MP4-сегментов и выгрузка в S3 (нужны параметры `MTS_S3_*` в `conf.env`); у муляжей архива нет |
| `test` | `{ "size": "1280x720", "rate": 10, "noise": 20 }` | только для муляжа: разрешение, кадров/с, шум |

Ошибочная строка (неверный `id`, `source`, повтор `id`) пропускается, причина пишется в лог,
остальные камеры работают. Если файл сохранён с ошибкой JSON — сервер оставляет камеры как были
и пишет ошибку в лог; исправьте файл и сохраните снова.

Другой путь к файлу: `VIDEO_CAMERAS_FILE=/путь/cameras.json` в `conf.env`.

## 7. Сколько камер потянет сервер

ffmpeg каждой камеры работает постоянно и перекодирует кадр раз в `min(previewIntervalMs, fullIntervalMs)`
(по умолчанию раз в секунду), даже когда никто не смотрит. Доставка кадров клиентам почти не нагружает сервер.

Замер на MacBook Pro (10 ядер), муляжи 1280×720 @ 10 кадров/с, 2 клиента, 60 с:

| Камер | Доставлено | Задержка ср. | Трафик на клиента | CPU ffmpeg | CPU сервера | Память ffmpeg |
|---|---|---|---|---|---|---|
| 1 | 100 % | 1 мс | 25 КБ/с | 6 % | 0,3 % | 39 МБ |
| 4 | 100 % | 1 мс | 50 КБ/с | 21 % | 0,5 % | 159 МБ |
| 8 | 100 % | 1 мс | 83 КБ/с | 41 % | 0,8 % | 309 МБ |
| 16 | 100 % | 1 мс | 150 КБ/с | 73 % | 1,2 % | 648 МБ |

CPU — в процентах от одного ядра. Реальная камера с основным потоком Full HD нагружает
сильнее муляжа (декодирование H.264/H.265), с дополнительным потоком — сопоставимо или меньше.

Проверить свою машину до покупки камер:

```bash
node tools/videoLoadTest.js --cameras 1,4,8,16 --clients 2 --duration 60 --size 1920x1080 --rate 25
```

Если не хватает CPU: дополнительный поток камеры, больше `fullIntervalMs`, меньше `maxWidth`,
`VIDEO_DECODE_KEYFRAMES_ONLY=true` в `conf.env` (декодировать только ключевые кадры).

## 8. Если что-то не работает

| Признак | Причина и решение |
|---|---|
| Клиент: `ERR_CONNECTION_REFUSED` на `ws://…:9202` | сервер не запущен или слушает другой порт — запустите `npm start`, сверьте `WSD_PORT_IN` в `conf.env` с адресом в клиенте; на macOS разрешите node входящие подключения в файрволе |
| Вкладка «Видеонаблюдение»: «Камеры не настроены» | dID пользователя нет в `dID` камер (раздел 1.3) или `minLevel` выше уровня пользователя; либо `VIDEO_MOCK_CAMERAS=0` и нет `VIDEO_RTSP_URL` |
| Не найти `cameras.json` | путь — в строке лога `init: камер N из …`; папка с точкой скрыта в Finder (`Cmd + Shift + .`) |
| Лог: `переменные окружения терминала перекрывают conf.env` | параметр задан в настройках терминала — раздел 1.2, «Если сервер пишет…» |
| Лог: `ffmpeg не найден` | установите ffmpeg (раздел 1.1) или укажите путь в `FFMPEG_PATH` |
| Карточка «Ожидание кадра…» дольше 30 с | ffmpeg не может открыть поток — ищите в логе `[VideoStreamService:camXX]`; проверьте адрес командой из шага 4 |
| `401 Unauthorized` в логе камеры | неверный логин/пароль или не закодированы спецсимволы пароля |
| `Connection refused` / `timed out` | неверный IP или порт, RTSP выключен в камере, камера в другой подсети |
| `404 Not Found` / `method DESCRIBE failed` | неверный путь потока — сверьтесь с таблицей шага 3 |
| Карточка «Нет сигнала» | кадры перестали приходить (камера отключилась); сервер сам перезапускает ffmpeg — в логе `нет кадров … перезапускаем ffmpeg` |
| Изменения в `cameras.json` не применяются | в логе `с ошибкой — камеры без изменений`: в файле ошибка JSON (лишняя/пропущенная запятая, кавычки) |

Состояние всех камер (статус, перезапуски ffmpeg, отправлено кадров) администратор может получить
запросом `get/videoStatus`.
